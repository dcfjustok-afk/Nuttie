## 1. 项目使命

为 Owner 与其朋友构建一款跨 iOS、Android 和 mobile H5 的营养、自律和体重管理产品，用公开可验证的“自律茄子”完整能力地图作为对标范围，通过分阶段交付实现可替代的个人使用体验。客户端仍以本地优先捕获为核心，但通过明确的账号与 PostgreSQL 同步边界支持跨设备延续。

Nuttie 不追求建立互联网平台。首期只建设满足认证、同步和数据生命周期所需的最小 API 与 PostgreSQL，不引入社交、实时协作、运营后台或远程 Push。除用户明确主动发起的 AI 请求外，AI key 和原始 AI 载荷不进入云同步；营养标签照片按 D-014 每次预览并确认；其他 AI 载荷是否采用同等逐次预览仍待 D-033。

## 2. 成功定义

项目同时满足以下条件才算成功：

1. 24 类、66 项竞品证据地图均有稳定 ID、来源、可信状态、本地化策略和需求去向。
2. 所有公开已证实能力与必要本地替代项均进入总范围，不通过静默删减来压缩交付。
3. 离线状态下，除 AI 外的核心旅程可以完整运行；联网恢复后，离线 mutation 可观察、可重放且幂等地同步到另一设备。
4. AI 只能由集中式 `AITransport` 发起且必须由用户主动操作；营养标签照片发送前展示内容与目标并按 D-014 逐次确认，其他 AI 载荷按待决 D-033 执行。
5. native 业务数据以 SQLCipher 加密保存，数据库密钥由本设备 Keychain 保护；Web 使用独立的 IndexedDB/WebCrypto/XSS/CSRF 威胁模型。
6. 加密备份可完成导出、导入、错误密码、损坏文件和版本迁移测试。
7. 真实协作事件、角色交接、审查意见、风险和 Owner 决策可由本地 JSONL 事件流追踪并在工作台查看。
8. iOS/Android/Web 的候选构建分别通过平台矩阵、权限、断网、恢复、同步冲突和可访问性验证；TestFlight 仅在未来获得明确授权后作为 iOS 分发渠道。

## 3. 范围

### 3.1 范围内

- 公开可验证的竞品能力及其本地可行替代。
- 餐食、营养、每日目标、体重、饮水、运动、提醒、洞察和设置等本地能力。
- AI 图片、文字、标签解析、营养分析、食谱或饮食方案等由用户主动触发的联网能力。
- 台湾食药署、USDA Foundation/SR 和用户自建食品组成的本地食品数据能力。
- Files 签名数据包导入、加密备份导出/导入和本地/云端数据删除。
- iOS 17+ native 下限、Android/Web 待 G4 冻结的最低支持矩阵、所有平台首发简体中文；TestFlight 不构成当前发布承诺。
- 项目文档、阶段门禁、RACI、事件流、消息记录、静态快照和 PM 汇报。

### 3.2 不在当前承诺内

- 公开资料无法验证的 9 项竞品细节。这些是机会项，不是竞品事实；经产品论证可成为 Nuttie 自有需求。
- 首版 HealthKit；该能力进入第二阶段独立决策。
- 会员计费、社交、社区、排行榜、广告、实时协作和远程 Push。
- 超出 D-073 最小认证/同步职责的后端、共享 AI 代理、对象存储、Redis、WebSocket、云任务队列或运营后台。
- 中国包装食品条码“全覆盖”承诺。
- 未取得明确再分发许可的数据抓取与内置。
- 长期 iOS 分发渠道；稳定后另行决策。

## 4. 产品与技术原则

1. **Owner 决策优先**：具体产品、架构、数据、隐私、设计与分发选择必须进入决策台账；建议不能自动升级为决定。
2. **本地优先且同步可见**：记录在本地缓存和离线 outbox 中先完成；认证/同步网络访问必须经过版本化 API、幂等、撤销、冲突和隐私审查。AI 网络访问仍只允许用户主动触发并通过安全审查。
3. **证据分层**：竞品事实只使用公开可验证证据；交叉来源、推断和未知项不得混写。
4. **完整地图、分段交付**：总范围保持完整，每个增量独立通过需求、设计、架构、安全和 QA 门禁。
5. **最小数据**：只收集实现认证、同步和当次功能所需的数据；不做遥测与行为画像，API 不接收 AI key。
6. **用户确认优先**：AI 结果必须可编辑、可拒绝，只有用户确认后的结构化数据才可进入业务记录。
7. **可追溯**：需求、设计、ADR、测试和交付证据使用稳定 ID 建立双向链接。
8. **真实状态**：工作台只展示实际发生的 Agent 任务、消息与审查，不制造常驻在线状态或虚假会议。

## 5. 已批准约束

本章程由 D-001 至 D-017、D-037~D-039、D-047~D-048、D-073 支撑，完整内容见 [decision-register.md](decision-register.md)。D-073 对 D-006、D-011、D-016 的冲突范围完成显式替代；本地缓存/加密备份、iOS 17+ native 下限与 `zh-Hans` 首发基线继续有效。其余已接受决定不能由团队自行覆盖。

### D-073 执行边界

- 客户端形态：Expo + React Native 覆盖 iOS、Android 和 RN Web/mobile H5；保持一套信息架构，在 320px 窄屏、横屏、平板、桌面和 1440px+ 大屏上调整密度，不复制三套产品。
- 数据形态：本地缓存 + 持久化 outbox 是离线工作边界；PostgreSQL 是已登录用户的同步权威。每条 mutation 带 `clientMutationId`、`deviceId`、`entityId`、`baseRevision`、`clientCreatedAt` 和 payload；append-only 事实默认合并，可编辑对象冲突显式呈现。
- 会话形态：Web 使用同源 HTTPS `/api` 与安全 httpOnly refresh cookie；native 使用平台安全存储，短期 access token 只在内存。账号删除、token/设备撤销、导出、恢复和隐私政策更新必须进入 G2/G4/G6 退出证据。
- 服务形态：首期版本化 REST + readiness；参考 Royal-Flush 的 Nginx 同源反代和私有 PostgreSQL。Redis、WebSocket、对象存储、后台、远程 Push 与服务端 AI 代理后置且需新决定。
- 工程形态：D-037 的 pnpm 11.18.0、`node-linker=hoisted`、唯一 `pnpm-lock.yaml` 适用于正式 monorepo；D-032 的 Expo/RN SDK 57 仍只是候选 Spike，不能自动解锁根工程或原生发布。

## 6. 阶段策略

| 阶段 | 目标 | 退出条件 |
| --- | --- | --- |
| Phase 0 | 公开调研、范围、体验、架构与质量基线 | G0-G4 PASS |
| Phase 1 | 本地核心日记闭环与基础数据 | 对应增量 G5 PASS |
| Phase 2 | AI 主动请求、离线条码与增强洞察 | 对应增量 G5 PASS，AI/数据安全审查通过 |
| Phase 3 | 系统集成候选与 Beta | G6 PASS；HealthKit 如需加入必须有新决策 |
| Phase 4 | 稳定分发与收尾 | G7、G8 PASS |

分期顺序是规划输入，不改变 D-017 的“完整范围不删减”。正式版本切片需在 G2 文档中形成并接受 Owner 审查。

## 7. 治理与授权

- Owner：范围、产品行为、设计方向、架构选型、数据/隐私边界与发布方式的最终批准人。
- 项目经理：组织角色、维护门禁、汇总风险、发出决策包、记录真实状态并向 Owner 汇报。
- 专业角色：在其职责范围内提出有证据的方案、替代项、风险和审查结论，无权替 Owner 接受候选决策。
- Git 提交、push、发布和线上变更：只有在 Owner 明确授权对应动作后执行。
