# 可追溯性与变更策略

## 1. 稳定 ID

| 对象 | 格式 | 示例 |
| --- | --- | --- |
| 来源 | `SRC-##` | `SRC-01` |
| 竞品证据项 | 领域前缀 + 编号 | `LOG-04`、`BODY-02` |
| Nuttie 功能 | `F-###` | `F-014` |
| 需求 | `REQ-###` | `REQ-027` |
| 非功能需求 | `NFR-###` | `NFR-006` |
| Owner 决定 | `D-###` | `D-015` |
| 架构决定 | `ADR-###` | `ADR-004` |
| 风险 | `R-###` | `R-003` |
| 测试 | `T-<LEVEL>-###` | `T-E2E-012` |
| 事件 | `EVT-YYYYMMDD-###` | `EVT-20260731-019` |
| 消息 | `MSG-YYYYMMDD-###` | `MSG-20260731-004` |

ID 一经发布不复用。对象被替代时保留旧对象并写 `supersededBy`。

## 2. 证据状态

- `CONFIRMED_IOS`：当前 iOS 公开页面或截图直接证实。
- `CROSS_SOURCE`：官方政策、协议或跨平台资料支持，但当前 iOS 界面未直接证实。
- `EVIDENCE_GAP`：公开资料无法验证。
- `CONFLICTED`：公开来源互相冲突。
- `NUTTIE_REQUIRED`：不是已证实竞品功能，但为满足本地闭环、安全或恢复所必需。

只有前两类可以被表述为竞品公开能力。`NUTTIE_REQUIRED` 必须明确标记为本地产品设计，不得伪装成竞品事实。

## 3. 追踪链

每项实现必须建立以下双向关系：

`来源/问题 -> 竞品证据 -> Nuttie 功能 -> 产品需求 -> 用户流程/界面状态 -> ADR/数据 -> 测试 -> 增量/发布证据`

允许一个对象关联多个上下游，但禁止只有实现没有需求，或只有需求没有验收测试。AI、备份、迁移、删除和权限需求必须额外链接安全审查。

## 4. 变更控制

1. 提交 `SCOPE_CHANGE` 或 `FACT_CORRECTION`，说明触发证据。
2. PM 识别受影响的需求、设计、ADR、测试、阶段和已交付数据。
3. 专业角色分别提供成本、风险、兼容性和隐私影响。
4. 若改变已接受决定、用户可见行为、数据边界或发布范围，提交 Owner 决策。
5. 批准后更新权威文档，旧结论标记为 superseded，不删除历史事件。
6. 对所有受影响产物重新审查；此前门禁可能回退到 `IN_PROGRESS` 或 `FAIL`。

## 5. 文件权威顺序

发生冲突时按以下顺序判定：

1. 最新且明确的 Owner 回复及其 `DECISION_ACCEPTED` 事件。
2. `docs/00-governance/decision-register.md` 与 `project-ops/decisions.json` 的一致副本。
3. 已通过门禁的产品、设计、工程和质量基线。
4. 工作台静态快照。
5. Agent 草稿、建议与历史报告。

若第 2 项两份副本不一致，停止依赖该决定并由 PM 修复，不自行猜测。
