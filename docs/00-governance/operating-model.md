# 团队运行方式

## 1. 组织模型

Nuttie 采用“按事件激活岗位”的小型互联网产品团队模型。岗位职责完整保留，但只有输入满足触发条件时才启动对应 Agent。每个角色必须留下任务、交接、审查、风险或验收证据；未实际运行的角色不会在工作台显示为活跃。

| 角色 | 激活条件 | 主要交付 | 当前映射 |
| --- | --- | --- | --- |
| Owner | 决策包、范围变化、门禁或发布授权 | 接受、拒绝、补充约束 | 用户本人 |
| 项目经理 / PMO | 项目启动、门禁、风险、跨角色冲突 | 计划、事件流、决策包、Owner 汇报 | `/root` |
| 产品经理 / 竞品研究 | 新证据、范围基线、需求变化 | 证据矩阵、能力地图、PRD、验收标准 | `/root/competitor_pm_v2` |
| 产品设计 | 产品范围可供建模或流程变化 | IA、用户旅程、状态、原型、无障碍 | `/root/product_designer_g3` |
| 移动端架构 | 技术可行性、数据或原生约束 | 架构、ADR、数据流、依赖候选 | `/root/mobile_architect_v2` |
| 隐私与安全 | 新数据、新权限、新网络或密钥路径 | 数据清单、威胁模型、审查结论 | G2-G4 草案后激活 |
| QA / 自动化 | 可验收需求或架构草案形成 | 测试策略、用例、缺陷、门禁结论 | 安全审查并行激活 |
| RN / iOS 工程 | 对应增量满足 Definition of Ready | 实现、测试、构建证据 | G4 PASS 后激活 |
| Release | Beta 候选、签名或分发事件 | 构建、分发、回退、发布说明 | G6 前后激活 |

Agent 名称是当前执行实例，不等同于永久人员身份。角色更换时必须发出 `ROLE_REASSIGNED` 事件并完成交接。

## 2. 决策权与 RACI

| 工作项 | A（最终负责） | R（执行） | C（协商） | I（知会） |
| --- | --- | --- | --- | --- |
| 项目使命与范围基线 | Owner | PM、产品 | 设计、架构、安全、QA | 全员 |
| 竞品证据与事实状态 | PM | 产品/研究 | 架构、QA | Owner |
| 产品需求与分期 | Owner | 产品 | 设计、架构、安全、QA | 工程、Release |
| 体验基线 | Owner | 产品设计 | 产品、架构、安全、QA | 工程、PM |
| 架构、数据与 AI 边界 | Owner | 架构 | 产品、设计、安全、QA、工程 | PM |
| 安全与隐私放行 | Owner | 安全 | 架构、产品、QA | 全员 |
| 增量实现 | 架构负责人 | RN/iOS 工程 | 产品、设计、安全、QA | PM、Owner |
| 测试与缺陷结论 | QA 负责人 | QA | 产品、设计、架构、工程 | PM、Owner |
| TestFlight / 长期发布 | Owner | Release | PM、QA、架构、安全 | 全员 |

`A` 不得被 Agent 自行代理。Owner 未明确答复时，结果保持 `CANDIDATE` 或 `DECISION_REQUIRED`。

## 3. 标准工作流

1. PM 创建带交付物、文件边界、输入与退出条件的 `TASK_ASSIGNED`。
2. 执行角色核对权威决定和证据，发现冲突时立即发出 `RISK_RAISED` 或 `DECISION_REQUIRED`。
3. 产出可审查草案后，发送 `HANDOFF_READY`，消息中必须列出稳定 ID、文件、已知缺口和请求审查的具体问题。
4. 下游角色发送 `ACK`，随后发送 `REVIEW_FEEDBACK`；沉默不算批准。
5. 作者逐条记录处理结果：接受、拒绝并说明理由、或升级 Owner。
6. QA 与安全独立审查。作者自测不能替代独立检查。
7. PM 根据客观退出条件提交门禁结论，只能是 `PASS`、`CONDITIONAL_PASS` 或 `FAIL`。
8. 需要 Owner 选择时，PM 在主 Codex 聊天中通过 `request_user_input` 每轮只弹出一个稳定 D 编号，解释各选项、推荐、代价和不决定的影响；Owner 点击选择卡后，PM 再进入下一题。
9. 对应增量达到 Definition of Ready 后才能进入实现。
10. 实现、测试、文档、迁移与已知问题一同接受 Definition of Done 检查。

Owner 的逐题选择在本批完成前只作为待回读输入，不立即发出 `DECISION_ACCEPTED`。PM 必须在批次末尾逐项规范化为 `ACCEPTED`、`CANDIDATE + SPIKE_AUTHORIZED` 或 `DEFERRED`，复述所有 Owner 事实输入，再通过原生选择卡请求 Owner 对整份解析做一次最终确认。D-032 的 A/B 只授权隔离 Spike，不能在这次回读中被误记为最终接受。工作台只展示候选、证据、沟通进度和已确认结果，不收集 Owner 选择，不生成回复模板，也不提供复制或下载决策答案的入口。若当前任务处于不开放 `request_user_input` 的 Default 模式，PM 必须请 Owner 切换到 Plan 模式，不得用网页表单或文字模板冒充原生选择卡。

## 4. 通信协议

### 4.1 事件与消息类型

| 类型 | 用途 | 必需响应 |
| --- | --- | --- |
| `TASK_ASSIGNED` | 分配边界清晰的工作 | `ACK` 或风险说明 |
| `HANDOFF_READY` | 上游产物可供下游消费 | 下游 `ACK` + `REVIEW_FEEDBACK` |
| `REVIEW_REQUESTED` | 请求指定角色审查指定问题 | 审查结论 |
| `REVIEW_FEEDBACK` | 记录接受项、问题、严重度和建议 | 作者处置记录 |
| `RISK_RAISED` | 新风险或假设失效 | PM 接收、分配 Owner/应对人 |
| `DECISION_REQUIRED` | 需要 Owner 决定 | Owner 明确选择或暂缓 |
| `DECISION_ACCEPTED` | Owner 已批准候选 | 更新权威台账与受影响产物 |
| `FACT_CORRECTION` | 已记录事实被新证据纠正 | 标记旧结论为 superseded 并重审下游 |
| `SCOPE_CHANGE` | 范围、阶段或优先级变化 | 影响分析与 Owner 批准 |
| `GATE_CHANGED` | 阶段门禁状态变化 | PM 报告证据与剩余条件 |

### 4.2 消息质量要求

- 使用稳定 `messageId`、`correlationId` 和 `relatedArtifacts`。
- 区分事实、建议、风险、假设和决定。
- 指明发送人、接收人、时间、需要的响应和响应截止阶段。
- 只记录真实发生的通信；总结必须能回链到原始 Agent 消息或工具事件。
- 敏感内容不得进入事件：API key、完整 prompt、AI 图片、健康数据和个人资料全部禁止记录。

## 5. Definition of Ready

一个实现增量只有同时满足以下条件才可进入工程：

- 需求具有稳定 ID、来源、业务规则、异常与空态、验收标准和阶段归属。
- 公开竞品事实与 Nuttie 自有增强被清楚区分。
- 关键用户旅程和相关界面状态已通过产品、设计和 QA 审查。
- 数据模型、迁移、权限、网络、备份和删除行为已明确。
- 所有会改变行为的候选技术或设计选择已经 Owner 接受。
- 安全和隐私审查没有未处置的阻断项。
- 测试层级、真机需求和可接受证据已定义。
- 外部依赖、许可证与 Mac/iPhone 前置条件已记录。

## 6. Definition of Done

- 实现与已批准需求一致，未加入未批准行为。
- 单元、组件、集成、迁移和适用的真实设备测试通过。
- 飞行模式证明非 AI 核心旅程无业务联网依赖。
- AI 请求经过适用的发送确认、最小化、校验、取消和错误路径测试；营养标签照片必须覆盖 D-014 的逐次预览，其他载荷按 D-033 最终决定验收。
- 文档、追踪矩阵、事件流、风险和已知问题同步更新。
- 无高严重度安全、隐私、数据丢失或无障碍缺陷。
- 代码审查与独立 QA 结论可追溯。
- 任何发布、上传或 Git 提交只在 Owner 明确授权后执行。

## 7. PM 向 Owner 汇报格式

每次阶段汇报依次包含：

1. 当前门禁与一句话结论。
2. 本轮真实完成物及其文件链接。
3. Agent 激活、交接与重要审查意见。
4. 证据数字、测试数字和残余风险。
5. 需要 Owner 决定时，只弹出当前一项的原生选择卡并给出推荐、备选和影响；不要要求 Owner 输入字母或复制整批模板。
6. 下一阶段在不同决定下会发生什么。

PM 不以过程篇幅替代结果，也不把“Agent 已完成”当成专业审查通过。
