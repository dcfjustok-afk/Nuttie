## 1. 目的与强制边界

本流程把 Owner 的“设计必须先原型后实现”要求转换为可审计门禁。任何会改变用户可见结构、入口、任务顺序、信息优先级或交互反馈的设计决定，都必须先经过候选原型、跨角色审查和 Owner 明确选择。

原型不是实现授权：

- 默认打开的方案只是预览起点，不代表推荐被接受。
- 点击 A/B/C 只改变当前浏览器内存中的预览，不写入决策台账。
- 设计角色不得依据可用性、自身偏好或实现便利替 Owner 选择。
- 未获得 Owner 的明确决定前，不得据原型初始化 React Native、创建正式路由目录、生成 `package.json`/lockfile/`ios/`，也不得注册 Apple 资源或执行发布动作。
- D-038 只决定产品导航外壳，不决定 D-018 的 Expo Router 或 React Navigation。

## 2. 适用范围

必须先原型后实现的项目包括：

- 主导航、信息架构落位和跨目的地返回行为；
- 首启、添加餐食、AI 发送预览、备份恢复、删除等关键任务流；
- 视觉方向、组件密度、状态表达、图表等价视图和无障碍顺序；
- 同一需求存在两种以上会实质改变用户行为的方案。

以下工作可在没有视觉原型时继续，但仍不能越过对应工程门禁：

- 事实调研、能力地图、领域对象、纯业务规则和测试设计；
- 与具体 UI 方案无关的安全边界、许可核验和失败不变量；
- 工作台、设计文档和不写入正式 App 工程的本地实验。

## 3. 角色与职责

| 角色 | 负责 | 不得执行 |
| --- | --- | --- |
| Owner | 比较候选、补充约束、接受/拒绝/暂缓最终方案 | 不需要代替团队补齐缺失状态或技术细节 |
| PM | 确认候选 ID、组织评审、记录明确回复、更新权威台账 | 把设计推荐或原型默认状态当作 Owner 决定 |
| Product Designer / DesignOps | 保持候选同等完整、制作原型、记录范围与已知限制、主持任务评审 | 因推荐项而降低其他方案完成度；直接改决定状态 |
| Product | 核对能力、分期、文案与证据边界 | 将研究缺口写成已确认竞品行为 |
| Mobile Architect / RN | 核对原生能力、状态边界和可实现性 | 用框架默认值反向决定产品外壳 |

## 4. 原型门禁

为避免与项目 G0~G8 混淆，原型流程使用 `PX-*` 检查点；它们不改变正式阶段门禁。

### PX-0：输入完整

进入条件：

1. 候选决定有稳定 ID、题目、互斥方案、影响和“不决定的后果”。
2. 相关能力、旅程、状态、安全边界和证据语言已有可引用基线。
3. 明确哪些内容在所有方案中保持不变，避免用功能缺失制造偏见。
4. 原型范围、保真度、设备范围和不可执行系统能力已声明。

D-038 的固定输入是：日记、趋势、食品资料、设置、情境新增、本地优先和 AI 可选边界。变化轴仅是入口组织。

### PX-1：同等完整候选

每个候选必须：

- 使用同一组任务、种子数据和状态；
- 能完成同一组评审任务，而不是只有推荐项可操作；
- 不使用更鲜艳颜色、更完整内容或更优文案暗示推荐；
- 在显著位置标记 `CANDIDATE`，不显示“已选择”“已批准”或投票结果；
- 不在 App 画布内放教学、营销或说服性说明。

对于 D-038：

- A 提供日记、趋势、食品资料、设置四个稳定目的地，新增动作随情境出现；
- B 提供日记、趋势、设置三个稳定目的地，所有新增任务集中到单一入口；
- C 以日记为中心，趋势、食品资料、设置和相关任务从更多菜单进入。

### PX-2：内部跨角色评审

至少完成以下检查：

- Product：所有固定能力和本地降级路径仍可到达；
- Architecture/Security：没有暗示后台联网、自动 AI、HealthKit 首版或云同步；
- QA/Accessibility：键盘、焦点、Escape、触控目标、动态内容、Reduce Motion 和 320/375/430 宽布局；
- DesignOps：三方案完成度、文案密度和种子数据相等，没有视觉诱导。

任何阻断发现都先修原型，再进入 Owner 评审。作者自测不能替代主 Agent 的最终浏览器验收。

### PX-3：Owner 任务评审

Owner 应在同一原型中按 A、B、C 分别执行：

1. 从今天的日记打开趋势，再回到日记。
2. 找到食品资料并查看本地食品来源。
3. 发起添加餐食、记录饮水或记录体重。
4. 打开设置中的 AI 与数据管理位置。
5. 判断日常任务是否过度集中、入口是否难以发现、返回行为是否符合预期。

记录内容包括：候选、任务、是否完成、首次寻找路径、困惑点、Owner 补充约束和最终处理（接受/拒绝/暂缓）。原型本身不保存评审结果，避免把一次点击误写成决定。

### PX-4：决定与设计基线

只有同时满足以下条件，候选才能进入实现基线：

1. Owner 以明确文字回复稳定 D 编号和单一选项，或给出可规范化的具体约束。
2. PM 逐项回读解析结果，确认没有把原型状态、推荐或沉默当作批准。
3. 权威 `decision-register.md` 与机器副本更新，并产生可追溯的 `DECISION_ACCEPTED` 事件。
4. Product Design 将接受方案、返回行为、状态和无障碍顺序形成正式规格。
5. Product、Architecture、Security 和 QA 对受影响基线完成复核。

若 Owner 选择“暂缓”，D-038 保持 `CANDIDATE/DECISION_REQUIRED`；低保真研究可继续，但正式导航外壳和路由目录保持阻断。

D-039 于 2026-08-15 满足上述 PX-4 条件：Owner 明确选择 A，权威决定与事件已登记，首层层级、返回、状态和无障碍顺序已冻结，Product/Architecture/Security/QA 复核为 PASS。该结果只进入 [D-039 PX-4 设计基线](d039-px4-design-baseline.md)，PX-5 与正式实现仍保持关闭。

### PX-5：实现 Definition of Ready

实现前还必须具备：

- 接受后的设计规格和稳定页面/状态 ID；
- 对应验收标准、异常/空态、动态字体与 VoiceOver 顺序；
- D-018 等独立技术决定已按自身门禁处理；
- 测试可观测性标识与返回/deep-link 契约；
- 无未处置的安全、隐私或数据完整性阻断项。

达到 PX-5 只允许进入对应增量实现，不等于授权 commit、push、TestFlight 或发布。

## 5. D-038 评审量表

三套方案使用相同量表，不做加权推荐：

| 维度 | 评审问题 | 证据 |
| --- | --- | --- |
| 可发现性 | 日记、趋势、食品资料和设置能否在合理路径内找到 | 首次路径与误入路径 |
| 新增效率 | 添加餐食、饮水、运动和体重是否易于发起 | 操作步数与返回结果 |
| 本地优先感知 | 手工、本地食品和本地趋势是否明显独立于 AI | 任务完成与文案理解 |
| 信息密度 | 小屏上是否容易扫描且没有入口拥挤 | 320/375/430 视口记录 |
| 返回预期 | 从食品资料、趋势、设置和新增任务返回是否可预测 | 返回目标与焦点位置 |
| 无障碍 | 键盘、VoiceOver 顺序候选、焦点与控件名称是否完整 | QA 清单与问题记录 |

量表结果用于解释取舍，不自动计算胜出方案。
