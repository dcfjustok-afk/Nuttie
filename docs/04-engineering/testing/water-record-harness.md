# 饮水记录事务与当日汇总合同

> 状态：`SPIKE / FRAMEWORK_AGNOSTIC / NON_PRODUCTION`
>
> 对应能力：F14、REQ-F14、AT-F14；对应旅程：J-06
>
> 已确定边界：首版本地手工记录，并能查看当日汇总

## 1. 目的与结论

`tools/water-record-harness.mjs` 建模 F14 当前唯一可安全实现的部分：用户手工写入一条容量事实，之后可以修改或删除；给定一个明确的本地日历日，可以从完整记录集合精确重算当日汇总。

合同固定以下不变量：

- 保留用户输入的原始十进制字符串、单位 ID 和版本化测量定义；
- 单位换算必须由调用方逐条显式提供为有理数，记录同时保存不可变换算快照和精确基准量；
- 核心合同不内置默认单位、显示单位、快捷量或杯制式，因此不能借工程实现替 Owner 做产品选择；
- `localDate` 必须与带显式 offset 的 `recordedAt` 日历部分一致，不隐式读取设备时区；
- 创建、修改和删除使用 revision compare-and-swap；跨日修改必须同时返回旧日与新日的重算证据；
- `commandId` 与不可变命令指纹绑定，提交后回执丢失只能回放同一事务，不能重复累计容量；
- 回执包含完整记录集合、受影响日期、每日汇总及各自指纹，不能只证明目标行存在；
- 同一版本化单位定义中，相同单位 ID 的换算因子必须一致；不兼容的测量定义保持分组，绝不静默相加。

## 2. 单位与汇总边界

调用方输入的单位定义包括 `definitionId`、`unitId`、`baseUnitId` 和到基准单位的精确分数。它是事实随记录保存的换算证据，不是产品默认值注册表，也不表示 UI 必须提供其中任何单位。

当日汇总只合并 `definitionId + baseUnitId` 相同且定义内部一致的记录。不同定义分别返回，等待上层在已批准的产品规则下处理。空日返回 `status = EMPTY`、`recordCount = 0` 和空 totals；合同拒绝零容量记录，不用伪造一个零值事实表达“未记录”。


## 4. 尚未授权的内容

- 快捷量、饮水目标、默认/展示单位、显示精度、撤销交互和趋势规则仍待 Owner。
- 本合同没有饮水建议、达标率、健康判断、提醒或自动生成记录。
- HealthKit、传感器或其他自动来源不在首版授权内。
- SQLite/SQLCipher repository、迁移、组件、无障碍与真机证据必须在获授权工程阶段完成。
